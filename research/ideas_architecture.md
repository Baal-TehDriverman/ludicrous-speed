## Idea 1: Successor Chains for Graceful Degradation

**Concept:** Extend the supervisor/subordinate structure with pre-declared successor nodes — a chain-of-command succession plan baked into the graph. When a node goes offline (removed from graph, inactive in activity poll, or flagged by the operator), its subordinates automatically reassign to the declared successor instead of becoming orphans. The existing `normalize` function already derives subordinates from supervisors and detects orphans implicitly; this adds an explicit `successor` field per node that `normalize` validates (no cycles through successor links, must be known profile, cannot be self, cannot be a current subordinate) and `save_graph` uses to auto-rewire on node removal. The `POST /simulate` endpoint already models chain-of-command; extend it to accept `failed_nodes=[...]` and model successor promotion through the chain, returning the resulting tree.

**Files touched:**
- `fleet_graph_core.py` — add `successor` field to node schema; extend `normalize` to validate successor chains (no cycles); new `resolve_successor(graph, failed_node)` returning the promoted successor or None; extend `save_graph` to accept a `removed_profiles` list and auto-rewire their subordinates to declared successors; extend `describe` to include `successor` in output
- `dashboard/plugin_api.py` — new `GET /successors` (current successor map); `PUT /successors` (set successors for multiple nodes); extend `POST /simulate` to accept `failed_nodes=[...]` and model successor promotion through the chain; extend `PUT /graph` to accept `removed_profiles` and trigger auto-rewire
- `desktop-plugin/plugin.js` — node inspector gets a successor picker (dropdown of eligible profiles — peers, supervisor's peers, or same-level nodes); graph canvas shows successor arrows (dashed, distinct color from supervisor solid arrows); removal/offline notification in deck view offers "auto-rewire via successor" action; simulation results panel shows successor promotion paths

**Why it matters:** The fleet's 75-node DAG has four co-equal roots (baal, lilith, lucifer, yeshua) and deep subordinate trees. When any node goes offline — a profile uninstall, a Hermes restart, a crashed bot — its subordinates become orphans with no communication path. The existing graph validates on write but doesn't handle runtime node loss. Successor chains turn the static topology into a resilient structure that degrades gracefully: a node's death promotes its successor, subordinates follow, and the tree stays connected. This is the graph analogue of the simulation endpoint's chain-of-command modeling — but for failure, not planning.

## Idea 2: Capability-Weighted Delegation with Semantic Matching

**Concept:** Extend `can_delegate_to` from pure structural feasibility (subtree depth, subordinates exist) to capability-aware delegation. Each graph node carries optional `capabilities` tags (e.g., `["coding", "research", "modding", "legal"]`); when a supervisor delegates, the recipient's subtree is scored by capability match against the task description, and the best-matching subordinate within the subtree is suggested as the delegation target. Uses the existing `/match` endpoint's semantic routing (local fastembed via `mixedbread-ai/mxbai-embed-large-v1`, zero API cost — already in `plugin_api.py` lines 239-334) to score candidates, so no new model, no API cost. Capability tags are stored on the graph node (not a separate system), so they're part of the SSOT and survive rewire. The `_capability_summary` function (lines 150-217) already derives what each bot is good at from profile files; capability tags are the operator-override layer on top of that derived summary.

**Files touched:**
- `fleet_graph_core.py` — add optional `capabilities` field to node schema (list of strings, validated non-empty if present); new `capability_score(graph, task_description, candidate_profile)` returning a float 0-1 using embedding similarity (reuses the `/match` fastembed path — pure graph + embedding, no profile reads); new `best_delegation_target(graph, sender, task_description, contract=None)` returning `(recipient, score, reason)` — walks the sender's subordinate subtree, scores each node by capability match, returns the highest-scoring node that also passes `can_delegate_to`
- `dashboard/plugin_api.py` — extend `POST /send` (delegate kind) to accept `task_description` and return the capability-scored target suggestion (or accept an explicit target and return the match score as confirmation); new `GET /capabilities/{p}` returning a node's declared capabilities; extend `GET /match` to accept a `subtree=` filter so capability search is scoped to a supervisor's tree
- `desktop-plugin/plugin.js` — node inspector gets a capabilities editor (tag input, suggested from profile's SOUL/skills via `rosterCap`); delegation composer gets a task description field; after composing, the UI shows capability-matched target suggestions from the subtree with match scores; delegation notice includes the task description and the match rationale

**Why it matters:** The fleet already has semantic routing (`/match`) and structural delegation (`can_delegate_to`). But today, a supervisor delegating downward picks a recipient by name — knowing who's who in a 75-node tree is cognitive load. Capability-weighted delegation turns the org chart into a queryable skill map: "who in my tree is best at modding?" gets a scored answer without the supervisor needing to remember. The capabilities are declarative graph data (not inferred, not external), so they're auditable, editable, and survive rewire — the same SSOT principle that governs supervisors and peers.

## Idea 3: Peer Mesh Fallback Routing with Supervisor Chain Backup

**Concept:** When a peer-to-peer message can't be delivered (recipient inactive, inbox full, or the peer relation exists but the direct send is blocked), automatically route through an alternative peer path or fall back up to the sender's supervisor and back down to the recipient — whichever is shorter. The existing `can_communicate` is binary (allowed/blocked) and `chain` finds the supervisor-path between two nodes. This adds `peer_path(graph, relations, sender, recipient, max_hops=3)` that finds alternative peer route through the mesh (BFS over peer edges), and `fallback_communicate(graph, relations, sender, recipient)` that returns the best available route (direct peer, peer mesh, or supervisor chain) with the route type and hops. The `POST /send` endpoint already validates and delivers; extend it with a `fallback=true` option that uses the best available route and returns which route was chosen.

**Files touched:**
- `fleet_graph_core.py` — new `peer_path(graph, relations, sender, recipient, max_hops=3)` returning a list of peer hops (profile -> peer -> peer -> ... -> recipient) or None; new `fallback_communicate(graph, relations, sender, recipient)` returning `(route_type, path, hops)` where route_type is "peer" (direct), "peer_mesh" (multi-hop peer), "supervisor_chain" (up then down), or "blocked"; uses existing `can_communicate` for direct, `peer_path` for mesh, `chain` for supervisor fallback; pure graph + relations, no profile reads
- `dashboard/plugin_api.py` — extend `POST /send` to accept `fallback=true` (default false — preserves existing behavior); when fallback=true and direct send is blocked, compute fallback route, deliver along it, and return `route_type` + `path` in the response; new `GET /route/{sender}/{recipient}` dry-run endpoint returning the best available route without delivering; extend `GET /traffic` to tag messages delivered via fallback with `route_type`
- `desktop-plugin/plugin.js` — message composer shows fallback route preview when the direct peer send is blocked (user sees "direct peer blocked — fallback: lilith -> hermes -> spock, 2 hops"); sent messages in the inbox show a route badge (direct / peer_mesh / supervisor_chain) when delivered via fallback; fleet operator settings toggle default fallback behavior (on/off/per-message)

**Why it matters:** The fleet's peer relations (Data↔Spock, Worf↔Tuvok, Lucifer↔Yeshua) are static — declared once, used for sideways messaging. But the peer mesh is a graph, not a single edge: if Data can't reach Spock directly (Spock is busy, offline, or the edge is temporarily unhealthy), the mesh may have an alternate path (Data -> Picard -> Spock's peer -> Spock) or a supervisor fallback (Data -> Picard -> Spock). Without fallback routing, a blocked peer message is just blocked — the sender gets an error and retries manually. With fallback routing, the graph's structure becomes a resilient communication fabric: the peer mesh has redundancy, and the supervisor chain is the backup spine. This is the messaging-layer analogue of successor chains' topology resilience — same principle, different layer.
